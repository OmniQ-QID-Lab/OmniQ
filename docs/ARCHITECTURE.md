# Architecture

Residual Agents (RA) is one Python orchestrator that runs every agent role as a separate session of DeepSeek's agent
CLI, DSH, on the same model. The orchestrator plans nothing itself: it starts sessions, reads the files they write,
applies fixed rules to their verdicts, and keeps the whole record on disk. This page explains how one run works. The
terms are defined in [GLOSSARY.md](GLOSSARY.md); the settings are in [CONFIGURATION.md](CONFIGURATION.md).

## 1. Parts and where they live

| paper term | in the code |
|---|---|
| planner | `plan` and `replan` sessions; the plan validator `validate_plan`; `get_plan` |
| executor | `exec`, `restart`, `cont`, `resume` and `fix` sessions; `unit_worker` drives them |
| critic | `critic`, `criticd`, `criticcp` and `criticfmt` sessions; `run_critic`, `run_checkpoint`; `machine_critic` writes repair orders without a model |
| probe agents and critic panel | `scout1..3` and `criticsel1..3` sessions; `scout_round`, `scout_select` |
| report | the render unit: `report_render` session and its review; `run_report` |
| experience layer | the four memory files in `residual_agents/memories/`; `load_notes` and the residual retrieval (`bank_pick`) |
| experience distiller | not in the code: the memories were written between development rounds and approved by a human expert |
| judge agent | not in the run: `infra/judge/` runs it afterwards ([JUDGING.md](JUDGING.md)) |

The orchestrator is a single module, `residual_agents/orchestrator.py`, generated by `tools/build.py` from the files
in `fragments/` (one shared namespace; do not edit the generated file). The fragments group the code by concern:

|---|---|

| `01_util` | file, log and ledger helpers; node facts (`NCPUS`, `MEM_GB`) |
| `02_dsh_backend` | DSH patch files, version, model id, proxy switch, per-session home and environment; the prompt-file launcher |

| `06_clock_taskbook` | the clock, the report reserve, the TASK BOOK parser |
| `07_checks` | deliverable and handoff checks, `mech_check` |
| `08_jobs` | waiting on registered background jobs |
| `09_prompts` | every prompt constant (frozen text) |
| `10_planner` | plan validation and acceptance, `READINGS.md`, unit specs, the run state file |
| `11_memory` | memory loading and residual retrieval |
| `12_critic` | audits, report parsers, the machine critic, checkpoints |
| `13_restart` | archiving and fresh attempts |
| `14_scouting` | probe agents and the panel |
| `15_readings` | reading changes and input-change propagation |

`residual_agents/trace.py` renders the timelines; `residual_agents/cli.py` is the `ra` command, a thin wrapper that
never changes what the orchestrator does.

## 2. One run from start to end

The orchestrator reads no command-line arguments. It is configured by environment variables and works in fixed
container paths: the run folder is mounted at `/workspace` (the prompts name this path) and the episode store at
`/pece_store`.

1. **Start.** Ledger event `episode_start` (model, DSH version, wall, cores, memory, GPUs, clock settings). The
   orchestrator then parses the task specification `/workspace/CLAUDE.md` into the task book (`task_book` event) and
   loads the four memory files (`notes_loaded` event with the hash of each file).
2. **Plan.** The planner writes `/workspace/_pece/plan.json`; the validator accepts it or sends it back (section 4).
3. **Schedule.** The main thread runs the scheduling loop. Each unit runs in its own thread (section 6). An override
   thread keeps the clock and writes `_pece/clock.json` every minute; a sampler measures the memory of the run's
   processes every 30 seconds.
4. **Override.** When the remaining time falls to the report reserve (75 minutes) plus a 15-minute flush window, the
   override fires: running executors are told to wrap up, open reviews and scouting stop. With the paper's wall of
   85,800 s this happens about 22.3 hours into the run.
5. **Report.** After the flush (at most 15 minutes) the report agent writes `report.md` and the figure, and a critic
   reviews them (section 10).
6. **Epilogue.** `token_usage.json`, the store record and `_pece/digest.md` are written, then `episode_end`, then the
   timelines.

Exit codes: 0 normal end; 2 configuration error (missing memory folder, direct mode without a key, or
`PECE_PLAN_ONLY=1` without a valid plan); 3 infrastructure failure, with the marker `/workspace/.infra_failure` (the
backend stayed unreachable, or a second start in the same folder was refused); 128 + signal number after SIGTERM,
SIGINT or SIGHUP. Any exception in the main body fires the override, flushes and still runs the report. A
delivered `report.md` is never voided by a later infrastructure failure.

## 3. The call layer: one session per call

Every role is one call of `run_call(prompt, timeout, tag, ...)`, and every call is one fresh DSH session
(`dsh --profile headless --patch <patch file>`). DSH cannot resume a headless session, so a continuation is a new
session that quotes the tail of the previous transcript.

**Prompt.** `_assemble` puts a header before the role prompt:
- `TIME LEDGER`: wall, elapsed and remaining time, the report reserve, units done, and this unit's calls, waits and
  grades so far;
- `NODE`: cores, memory and GPUs; `RESOURCE GRANT`: the session's own cores and memory, if granted;
- `TASK BOOK`: the judged lines of `CLAUDE.md` numbered F1 to Fn (Objective, General Guidelines, Figure Fidelity
  Standard, Paper-Specific Preliminaries, Deliverables), the other sections as context, and the judging rules
  (windows and tolerances are gates, display settings are targets, a permitted reduced scale is judged at that
  scale); capped at 64,000 characters;
- for a continuation: the previous session's transcript tail (at most 3,500 characters), the files it wrote, the
  log tail and the head of the handoff.

After the role prompt come fixed hints: `DSH_EVIDENCE_HINT` always, `DSH_SESSION_HINT` for executors, and
`TEXT_ONLY_HINT` only when image input is off.

**Time limit.** Every call is clamped to the clock:
`timeout = max(60, min(timeout, max(600, remaining - report_reserve - 300), remaining - 120))` seconds. Most
non-executor calls are sized by `slot(want) = max(300, min(want, remaining - 900))`.

**Launch.** The prompt goes to DSH through a small launcher, `_pece/dsh_argv.mjs`, which reads it from
`.dsh_ra3/calls/NN_<tag>/prompt.txt`, so that the prompt never appears on a process command line, where an agent's
`pkill -f` could match it. If the launcher fails, the run falls back to
passing the prompt as an argument. The session runs in the unit folder (planners in `/workspace`), in its own process
session, with its output in `_pece/logs/NN_<tag>.log` and its DSH home in `.dsh_ra3/calls/NN_<tag>/`.

**Environment of a session.** A copy of the orchestrator's environment, plus: `DSH_HOME`; `DEEPSEEK_BASE_URL` and
`DEEPSEEK_API_KEY` (proxy mode: `http://127.0.0.1:$DSH_SHIM_PORT/v1` and a dummy key; direct mode: passed through);
`DSH_PERMISSION_MODE=danger-full-access` (the agent runs every command without asking); `DSH_TELEMETRY_DISABLED=1`;
the process markers `PECE_CALL_TAG=<RUN_ID>:<tag>` and `PECE_UNIT=<RUN_ID>:<unit>`; with a grant, thread caps
(`OMP`, `MKL`, `OPENBLAS`, `NUMEXPR`, `VECLIB_MAXIMUM` and `JULIA_NUM_THREADS`) and `PECE_GRANT_CORES`,
`PECE_GRANT_MEM_GB`.

**DSH settings.** `_dsh_setup` writes `.dsh_ra3/gw_patch.yml`: the model id, reasoning effort `max`, a 30-minute
stream idle timeout, a 12-hour limit per shell command, the session-log upload and package inventory switched off,
and, with image input on, a model catalog entry that accepts text and images. Every critic tag uses
`gw_patch_critic.yml`, which is the same except that one shell command is cut after 600 seconds.

**Watchdog.** The orchestrator polls every 30 seconds. An override or flush request stops the session. At the
deadline an executor slice is extended by 1 hour, at most 3 times, while the unit is productive (a file under the
unit written in the last 15 minutes and no registered job alive; or, for the first extension only, at least 60
CPU-seconds in the last 5 minutes), at least 1 hour of usable wall remains, and no checkpoint is due. Otherwise the
session is stopped and `<<ORCH TIMEOUT>>` is appended to its log. Stopping means SIGTERM, a 12-second grace,
SIGKILL of the process group, then a sweep of every process that carries the call's marker, sparing the unit's
registered job. A flush stops only the DSH process, so computations keep writing.

**Accounting.** After the call, the orchestrator decodes the session log (`session.v3.jsonl.zstd`) with the `zstd`
program, the Python `zstandard` module or Node's built-in zstd, in that order, and sums the usage of every model step
and every retried request: uncached input, cached input, output (which includes reasoning) and reasoning. `tokens` =
uncached input + cached input + output, and `cost_usd` uses `RA3SR_RATES`. The usage includes DSH sub-agent sessions.
The ledger records a `call` event.

**Pens-down.** A planner, critic, probe agent, panel critic or report call that times out gets one short wrap-up
session (`<tag>_wrapup`) to save its work. An executor stopped by the override gets a wrap-up of 840 seconds; an
interrupted critic or planner gets its own wrap-up; interrupted probe agents and panel critics get none.

**Dead calls.** A call is dead when it used 0 tokens and either exited with an error (not a timeout or an interrupt)
or was an executor turn that ended normally; an executor call that wrote files under its unit while no registered job
ran is never dead. A dead call is held 120, 300 and 600 seconds and retried (`<tag>_gwretryN`). If it stays dead, the
endpoint is probed with a 1-token completion for up to 1 hour: if it answers, the call gets one more try; if not, the
run writes `.infra_failure`, fires the override and exits 3. A planner that stays dead on the first plan is an
infrastructure failure even while the probes answer.

## 4. Roles

| role | tag | time limit | output and parser |
|---|---|---|---|
| planner | `plan` | first call 3,600 s + 900 s pens-down; a fix of a rejected plan 1,200 s; at most 3 attempts in 6,300 s | `/workspace/_pece/plan.json` = `{requirements, readings, units}`; `validate_plan`; after the last failed attempt `_repair_plan`, then `_minimal_plan` |
| branch replanner | `replan` | at most 1,800 s | the same file plus `_pece/plan_diff.md`; finished, running and retired units are kept unchanged |
| executor, first launch | `exec_<uid>` | slice 7,200 s, extended while productive | `/workspace/<uid>/handoff.json`, optionally with a `waiting` block that registers a background job |
| fresh executor after a C | `restart_<uid>` | as above | as above, in a fresh folder |
| continuation | `cont_<uid>` | as above | continues a session cut at its slice |
| resume after a job | `resume_<uid>` | as above | continues after a registered job ended or stalled |
| repair round | `fix_<uid>` | first slice clamp(2 x estimate, 1,200, 7,200) s | applies the critic's fix list |
| critic, full audit | `critic_<uid>` | 2,700 s; one shell command at most 600 s | `/workspace/<uid>/critic_report.md`: line 1 `GRADE:` with A, B, C or D, line 2 `GATES: G1=.. G2=.. G3=..`, last line `FIX_PLAN: {...}`; `residual.md` after a C or D |
| critic, delta re-audit | `criticd_<uid>` | 1,800 s | the same format; after a B whose G1 and G3 passed, and for reopened units |
| critic, checkpoint | `criticcp_<uid>` | 1,500 s | `GRADE:` with W, B, C or D, for a unit whose job is still running |
| critic, format retry | `criticfmt_<uid>` | up to 900 s | a graded report when the first one could not be parsed |
| probe agents | `scout1..3_<uid>` | 2,700 s each, in parallel, each with a third of the cores and memory | `_pece/scouts/<uid>.sN/sK/candidate.json` (hypothesis, proof of concept, supports, plan, reading change) |
| critic panel | `criticsel1..3_<uid>` | 1,800 s each, in parallel | `select1..3.md` with `RANK:`, `ADOPT:` and `DISQUALIFIED:` lines |
| report agent | `report_render` | `max(600, min(max(5400, reserve + 600), remaining - 1620))` s | `report.md` and `reproduced_figure*` in `/workspace/render/`, copied to `/workspace/` |

All roles use the same model. The planner and critic prompts carry the planner and critic memories; executors,
probe agents and the report agent receive selected residual-memory entries (section 11).

## 5. Grades and the close rule

The critic checks three gates: **G1 provenance** (every reported or plotted number traces to data computed on disk by
code that is present; a series built from the paper's plotted values is fabricated), **G2 implementation** (the
method and conventions the task book fixes) and **G3 task book** (every required item this unit serves is met). It
grades **A** (pass), **B** (local repair), **C** (new approach), **D** (retire on task-book grounds) or, at a
checkpoint, **W** (on track).

The orchestrator applies fixed rules on top of the critic:
- a B with a G1 hit becomes a C: a fabricated or untraceable number is never patched in the same attempt;
- a D without an `F<n>` citation and an "(a)" or "(b)" ground becomes a C (ledger `d_rejected`; see KI-06 in
  [KNOWN_ISSUES.md](KNOWN_ISSUES.md));
- a W after a handoff is read as B; a checkpoint A is read as W; a checkpoint without a verdict is W while the job
  runs, otherwise a machine-written B.

**Only time closes a unit.** `decide` acts on the verdict while enough usable wall remains (usable wall = time until
the override):

| verdict | action |
|---|---|
| A | done |
| D | failed; dependent units are blocked; one branch replan per run if at least 3 hours of usable wall remain |
| B | repair in place while at least 35 minutes remain. If the same gates are hit with unchanged deliverables in 3 B rounds in a row, the B is treated as a C (see KI-05) |
| C | probe agents and panel if at least 16,500 s (4.58 hours) remain; otherwise repair in place with the residual while at least 35 minutes remain |
| any verdict, too late | settle in place: a B with all gates passing is done; a unit whose last full audit passed G1 is done with a known gap; a G1 hit fails; a valid handoff that was never reviewed is done with a gap; otherwise failed |

## 6. Life of a unit

`unit_worker` runs one thread per unit: execute, then (after a handoff) a mechanical check, then a wait on a
registered job or a review, then `decide`. A session cut at its slice is continued, never reviewed.

- **Outcome of an executor session** (`call_outcome`): `HANDOFF` (a valid new `handoff.json`), `HANDOFF_BAD`, `CUT`,
  `CUT_NOHAND`, `INFRA` or `INTERRUPTED`.
- **Mechanical check** (`mech_check`, written to `<uid>/mech.json`): the declared deliverables exist and parse
  (npz, npy, csv, json, h5, png, pdf, py, text), Python files written in the call compile, and the handoff is valid
  (a missing or unparseable handoff, a listed path that does not exist, an unusable `waiting` block, or a criteria row
  with `pass: false` and no `stopped` reason are hard failures; the rest are warnings). A failure starts a repair
  round with an orchestrator-written fix list ("MECHANICAL FINDINGS"), at most 6 times per unit.
- **Wait** (`wait_job`): no model call while a registered job runs. The wait ends on the job's done marker, the end of
  its process, a stall (no progress for 15 minutes with nothing running, or declared progress files silent for 60
  minutes with no data growth while processes still run), an orphan (registered process gone, others still running
  after 60 minutes), a due checkpoint, or the override.
- **Checkpoint** (`checkpoint_due`): at most 3 hours after the unit's last look (launch, restart or verdict), and once
  when a job's declared end lies beyond the usable wall; never under the override or with less than 35 minutes left.
  The critic reads the unit's state, its results so far, its pace and the scale it is running at.
- **Holds.** An `INFRA` outcome holds the unit 10 minutes and retries; five executor calls in a row that end within a
  minute without a handoff cause one 5-minute hold.
- **Faults.** An exception inside the unit loop is logged and the unit continues (at most twice), then settles.
- **Settle** (`settle`): stops the unit's processes, then sets the status. A failed unit gets a residual, its
  dependents are blocked and a replan is requested; a done unit's outputs are fingerprinted for change propagation.

## 7. New approach: probe agents and the critic panel

After a C with enough time, `scout_round` starts three probe agents in parallel, each with one fixed angle (for
example "the code and the data flow"). Each writes a hypothesis, a small proof-of-concept computation (about 30
minutes), whether the result supports it, a plan and an optional reading change into `candidate.json`.

Three panel critics then rank the candidates (`scout_select`). The DISQUALIFIED and ADOPT lists bind by majority. The
ranking is a Borda count over the three rankings: the winner is the supported, not disqualified candidate with the
best total. If a majority answers `RANK: NONE`, there is no winner. (The paper describes this step as a majority
vote.)

- With a winner and at least 3 hours 10 minutes of usable wall: the unit's folder is archived as `<uid>.rN/`; a fresh
  folder receives the spec, the files the critic marked reusable, the old code and the winner's files (`from_scout/`,
  adopted runners-up in `from_scout_K/`); then a fresh executor starts (`restart_<uid>`).
- With a winner but less time: the winner's files and plan are applied in place.
- Without a winner: repair in place with the residual and the list of refuted hypotheses.

A reopened unit is never archived.

## 8. Shared readings, change propagation and reopening

The planner fixes the shared interpretations ("readings") K1 to Kn that every unit must use, and the orchestrator
publishes them as `/workspace/READINGS.md`. A reading changes only through a critic's `FIX_PLAN.reading_change` or a
winning or adopted candidate's `reading_change`, each with an existing evidence file, and at most once per reading per
run (`apply_reading_change`; history in `_pece/readings.json`).

`propagate_inputs` compares content fingerprints (hashes of the heads and tails of files, not modification times) of
each finished unit's inputs: its `needs` files, its upstream deliverables and `READINGS.md`. A finished unit whose
inputs changed is flagged; running units see a CHANGE NOTICE in their next prompt or review. The scheduler reopens a
flagged unit when at least 2 hours of usable wall remain, at most twice per unit, starting with a delta re-audit.

## 9. Scheduler, resource pool and file gate

The scheduling loop (`schedule_loop`) applies a pending replan, reopens flagged units, launches ready units and waits
15 seconds. It returns when every unit except the report unit is finished.

- **Readiness** (`deps_done`): every dependency is done, or the dependency is still running but has a valid handoff
  and every file this unit needs has been unchanged for 30 minutes (the file gate). Such a provisional start is
  flagged in the prompt (see KI-01).
- **Resource pool** (`ResourcePool`): a launch gets its declared cores and memory if the declarations fit. After 15
  minutes of waiting (at once for repair rounds and probe agents) it gets `min(declared, max(2, free))` cores, so
  cores can be oversubscribed, and its declared memory if that still fits the other declarations or the measured free
  memory (90% of the node minus the memory of this run's processes). Otherwise a first launch keeps waiting and a
  repair round takes what is really free (at least 4 GB). There is no CPU pinning; threads are capped through the
  environment. GPUs are not pooled; the `NODE` line names them.

## 10. Override, flush and report

`fire_override` tells running executors to wrap up (their DSH process is stopped and a wrap-up session follows) and
stops critics, planners and probe agents; `flush_wait` waits up to 15 minutes and then stops what is left.

`run_report` marks the report as started (the usable wall becomes 0), runs the report agent in the render unit,
copies `report.md` and `reproduced_figure*` to `/workspace`, checks them mechanically, retries once with a pointed
prompt if `report.md` is missing, and as a last resort writes a plain report itself if the backend still answers.
A critic then reviews the report: A ends it; B starts a repair round; C starts a fresh report (the old one is
archived as `render.rN/`); D keeps it. At most 3 repair rounds run, and only while more than 1,500 seconds remain.

The epilogue writes `token_usage.json` (totals and cost at `RA3SR_RATES`), the store record, `_pece/digest.md`, the
`episode_end` event and the timelines (`trace.py`). The digest skips agent-written ledger lines that are not JSON
objects.

## 11. The experience layer

`load_notes` reads four files from the memory folder (`residual_agents/memories/` by default, `RA3SR_NOTES_DIR` to
override), copies them to `_pece/notes/`, publishes `libraries.md` as `/workspace/LIBRARIES.md`, and records each
file's size and hash in the `notes_loaded` event. The memories are data: the code does not depend on their content.

| memory (paper term) | file | where it goes |
|---|---|---|
| planner memory | `planner_notes.md` (9 numbered lessons) | appended in full to the planner and replanner prompts |
| critic memory | `critic_notes.md` (9 numbered checks) | appended in full to full, delta and checkpoint audits, followed by a RESIDUAL INDEX with one line per residual entry |
| residual memory | `residual_bank.md`, entries R1 to R10, each a SIGNATURE, a CHECK and a FIX plus a `TAGS:` line (stages, events, keywords) | selected entries go into executor, probe-agent and report prompts |
| library table | `libraries.md` | `/workspace/LIBRARIES.md`; planner note 3 and R2 point to it |

Residual retrieval (`bank_pick`):
- first launch of a unit: R1 (always) plus the 3 best keyword matches against the unit and its spec;
- fresh attempt: up to 3 ids the archived round's critic cited, R1, one entry tagged for restarts and 2 keyword
  matches;
- repair, continuation and resume rounds: the ids in the current critic's `FIX_PLAN.residual_ids` (at most 4) plus
  up to 3 entries tagged with what just happened (a cut slice, a stalled or orphaned job, a mechanical failure);
- probe agents: the ids the critic cited plus R1; report agent: the entries tagged for the report (R10).

Each block is capped at 4,000 characters and recorded as a `bank_selected` event. Only the `residual_ids` field of the
last `FIX_PLAN` line is read. HTML comments in `residual_bank.md` are removed before entries are
parsed, so no prompt contains them. The comment records how the bank was consolidated during development and where
its entries came from (development runs, including the judge's feedback on development tasks); it never reaches a
prompt. The panel, the format retry and the machine critic get no memory.

A missing memory folder stops the run with exit code 2 before anything is written, and a folder with some
files missing runs with a warning and a `notes_missing` event (the ablation switch; see
[CONFIGURATION.md](CONFIGURATION.md)).

| `state.json` | units, last grades, failed and retired units, executor session ids, report state, override flag, last looks |
| `clock.json` | wall, elapsed, remaining, usable wall and unit status, rewritten every minute for the agents |
| `notes/` | the memories loaded |
| `dsh_argv.mjs` | the prompt-file launcher |
| `scouts/<uid>.sN/` | probe-agent work and panel votes |
| `digest.md`, `trace.json`, `timeline.html`, `timeline.txt` | summary and timelines |

**`/workspace/`**: `CLAUDE.md`, the paper PDF(s), `ENV.md` and, for some tasks, `skills/` (task inputs, staged by the
launcher; never `JUDGE.md`); `READINGS.md` and `LIBRARIES.md`; one folder per unit; archived attempts `<uid>.rN/`;
`render/`; the deliverables `report.md` and `reproduced_figure*`; `token_usage.json`; `.dsh_ra3/` (patch files and one
DSH home per session, with `prompt.txt` and the session log).

**A unit folder `/workspace/<uid>/`**: `spec.md` and `handoff_template.json` (orchestrator); `handoff.json`,
`validation.json` (the smallest-exact-case checks), `profile.json` (the timed representative step), code, data and
job files (executor); `mech.json` (orchestrator); `critic_report.md`, `residual.md` and probe files (critic or
orchestrator); `audit_rN/` (earlier reviews); `from_scout*/` (files from a winning probe agent).

**`/pece_store/`**: `ledger.jsonl` for all runs on the store, and `episodes/<RUN_ID>/` with `digest.md`, `meta.json`
and copies of the critic reports. Mount a separate writable folder per run or per user; it is not part of the run
folder.

## 13. Threads, locks and processes

Threads: the main thread (planner, scheduler, report), one per unit, the override thread, the memory sampler, and
during a new-approach round three probe-agent and three panel threads. Locks: `LEDGER_LOCK`, `CALL_LOCK`,
`STATE_LOCK` (the scheduler's condition), `PLANNER_LOCK`, `DSH_LOCK`, `READINGS_LOCK` and the pool's own lock; the
override thread never waits on `STATE_LOCK` for more than 5 seconds.

RA finds its processes by their environment markers (`/proc/<pid>/environ`), so it runs on Linux only, and the
orchestrator and the agents must share one PID namespace. Each concurrent run needs a unique `RUN_ID`, because the
markers contain it. The orchestrator stops every marked process of its run when it receives SIGTERM, SIGINT or
SIGHUP.
